## Research Question

Research https://github.com/GoogleCloudPlatform/open-knowledge-format comprehensively, then:
1. Parallels and differences with reflect.
2. Pros and cons (retrieval accuracy/efficiency, token usage) and how to measure them.
3. What can be lifted and shifted, and what it would take to support OKF as the standard in reflect.

## Executive Summary

OKF v0.2 is a storage and interchange convention (a folder of markdown files with YAML frontmatter, `type` the only required key), not a retrieval system. It explicitly declares serving, search and query infrastructure a non-goal. reflect is the opposite: a capture, index and recall engine whose on-disk unit (markdown + frontmatter) is already close to an OKF concept. The recommended path is to support OKF as an export/import projection (`reflect export --format okf`, `reflect ingest` of OKF bundles) while keeping reflect's retrieval engine, and to lift a handful of OKF ideas (derived trust tiers, `stale_after`, per-claim source footnotes, generated `index.md` browse surface).

## Key Findings

- OKF has no retrieval layer, no embeddings, no search, no token-budget guidance and no benchmarks. Its consumption model is progressive disclosure via per-directory `index.md` files that an agent reads and follows (SPEC §1, §8).
- reflect notes are markdown + frontmatter, so OKF conformance (§11: parseable frontmatter + non-empty `type` in every non-reserved `.md`) is mostly a backfill job. Measured on the live KB: 1,669 of a 3,000-note sample (56%) have no `type:` key, and the ones that do use two spellings (`LEARNING` 941, `learning` 389).
- reflect is richer than OKF on typed relationships (14-type entity sidecar), supersession (`superseded_by`, `is_latest`), confidence and scoping. These are exactly OKF's most-requested open issues (#16, #22, #11, #13), all unanswered by the single maintainer.
- OKF is richer than reflect on trust provenance semantics: `generated`/`verified` actors with derived trust tiers (unverified / machine-confirmed / human-reviewed), absolute `stale_after`, keyed per-claim source footnotes, and attested computations.
- Measurement gap in reflect itself: `recall_log.jsonl` records `injected_tokens` before the UserPromptSubmit hook truncates to 1,500 chars, so the logged figure (p50 2,879 tokens over the last 30 days) is not what the model actually receives. The "D → R, tok saved" economics rely on heuristic `discovery_tokens` defaults (e.g. 2,000 for corrections) because the drain writer does not set the field.
- Side finding: 176 of 677 recalls in the last 30 days (26%) fired on `<task-notification>` system text, logging ~599k tokens of recall output against queries that are not user intent.

## Detailed Findings

### External: OKF

- Maturity: v0.1 announced 2026-06-12, v0.2 ("trust signals") 2026-07-25. Standalone repo since 2026-08-11 (moved from `GoogleCloudPlatform/knowledge-catalog/okf`). 580 stars, 6 commits all by one maintainer, last push 2026-08-21, 16 open issues with no maintainer replies. Apache-2.0.
- Unit: the Concept (one `.md`); ID = file path minus `.md`. Bundle = directory tree, recommended distribution is a git repo.
- Frontmatter: `type` (required, free text), `title`, `description`, `resource`, `tags`, plus optional families: provenance `sources[]` (with `id`, `resource`, credibility signals), `generated {by, at}`, `verified [{by, at}]`, `status: draft|stable|deprecated`, `stale_after` (absolute ISO 8601), computation fields.
- Links: plain markdown links, untyped; broken links legal.
- Reserved files: `index.md` (progressive-disclosure listing, root may declare `okf_version: "0.2"`) and `log.md` (dated changelog).
- Attested Computation: sanctioned SQL + typed parameters + executor + deterministic attester. BigQuery-oriented.
- Tooling: Python reference agent (BigQuery + Gemini enrichment), a Cytoscape viewer, `trust_tier()`/`is_stale()` helpers, 39 tests. No JSON Schema, no validator, no other SDKs, no MCP or llms.txt tie-in.
- Benchmarks: none.
- Weaknesses: untyped edges, no supersession/deletion semantics, path-as-identity, `generated` conflates author and last editor (#28), inconsistent path semantics (#29), breaking change without version bump (#24), weak sample attester, no ACL or scale story, single-maintainer governance risk.

Sources: repo `SPEC.md` §1-§13; [GCP launch blog](https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing); [v0.2 blog](https://cloud.google.com/blog/products/data-analytics/okf-v0-2-adds-trust-signals); [GitBook](https://www.gitbook.com/blog/what-is-okf-open-knowledge-format); [SEJ](https://www.searchenginejournal.com/google-cloud-announces-the-open-knowledge-format/579253/); [MarkTechPost](https://www.marktechpost.com/2026/06/16/google-cloud-introduces-open-knowledge-format-okf-a-vendor-neutral-markdown-spec-for-giving-ai-agents-curated-context/).

### Codebase: reflect

#### Storage
- KB root `~/.learnings` (`src/reflect_kb/cli/learnings_cli.py:38-47`), notes in `documents/<id>.md` (`learnings_cli.py:449`), project and branch shards (`plugin/skills/recall/scripts/recall.py:421-459`).
- Canonical frontmatter: `plugin/assets/learning_template.md:10-62` (`type: learning`, `id`, `confidence` + `confidence_num`, `discovery_tokens`, `superseded_by`, `forget_after`, `provenance{...}`).
- Rule S9: frontmatter immutable after write; mutable signals live in `reflect.db` `learning_signals` (`learning_template.md:2-9`, `plugin/scripts/reflect_db.py:76-90`).
- Entity sidecar `<id>.entities.yaml` with 14 typed relationship kinds and bi-temporal edges (`plugin/references/knowledge_format.md:16-102`).
- Three ID schemes across writers (`learnings_cli.py:106-122`, `plugin/scripts/drain_extract.py:147-156`, `plugin/skills/recall/hooks/user_prompt_submit_recall.py:387`).

#### Retrieval
- Parallel vector + BM25 (qmd) + graph + date sources, RRF k=60, cross-encoder rerank with bounded boosts, MMR λ=0.7 (`recall.py:3080-3186`, `1474-1493`, `1834-1905`).
- Staged recall index → timeline → hydrate (`plugin/skills/recall/scripts/recall_stages.py:13-20`) is reflect's analogue of OKF progressive disclosure.
- Hook caps: UserPromptSubmit truncates at 1,500 chars (`user_prompt_submit_recall.py:102,595-596`); SessionStart 3 results / 1,500 chars (`plugin/skills/recall/hooks/session_start_recall.py:97-105`).
- The ranker does not read a note's `superseded_by` (only the edge-date filter mentions it, `recall.py:1396-1442`).

#### Economics and evaluation
- D/R metric: D = `discovery_tokens` or fallback defaults (`recall.py:400-407,831-865`), R = chunk chars / 4 (`recall.py:868-872`). Logged pre-truncation (`recall.py:2622-2657`).
- Retrieval harness: R@5, MRR, noise, latency over 20 golden queries (`tests/eval/harness.py`, `tests/eval/fixtures/golden_queries.yaml`); baseline R@5 1.0, MRR 0.9375, noise 0.2, p50 12.8s (`tests/eval/results/baseline.json`).
- LOCOMO pilot J = 0.80 on 50 questions (`tests/eval/locomo/REPORT.md:3-17`), ~$15 per run.

#### Interop
- Export is a custom tarball (`plugin/scripts/kb_export.py:6-45`); import in `plugin/scripts/kb_import.py`. No standard format export.
- `/reflect:ingest` already reads 11 foreign memory sources via providers (`plugin/skills/ingest/SKILL.md:43-59`); an OKF provider fits this pattern.

## Parallels and differences

| Concern | OKF v0.2 | reflect |
|---|---|---|
| Unit | Concept `.md` + frontmatter | Learning `.md` + frontmatter |
| Required keys | `type` | template: many; CLI `add`: title, category, key_insight |
| Identity | file path | `id` field (3 schemes) |
| Relations | untyped markdown links | 14 typed relations in entity sidecar, bi-temporal |
| Supersession | `status: deprecated` + prose | `superseded_by`, DB `is_latest`, `reverted` status |
| Trust | `generated`/`verified` actors, derived tiers | `confidence_num`, `proof_count`, `authority`, `quarantine` |
| Freshness | `stale_after` absolute instant | `forget_after` + recency boost |
| Provenance | `sources[]` + keyed per-claim footnotes | `provenance{}` + DB source quote/hash |
| Discovery | `index.md` progressive disclosure | hybrid vector/BM25/graph + rerank; staged index/timeline/hydrate |
| History | `log.md` | `learning_history` table |
| Distribution | git bundle | tarball (`kb_export.py`) |
| Retrieval spec | non-goal | full pipeline |
| Evals | none | golden harness, LOCOMO, 57 behavioural proofs |

## Retrieval accuracy and token usage (hypotheses to test)

- Accuracy [inference]: OKF index navigation depends on an LLM choosing from one-line descriptions. Plausibly strong on small curated bundles (the shipped samples total 78 files), weak at reflect's scale (7,785 documents) where lexical and semantic search matter. Falsified if an index-navigation agent matches reflect's R@5/MRR on the golden set.
- Tokens [inference]: a flat root index at ~25 tokens per entry would be ~195k tokens for 7,785 notes, so navigation must be hierarchical. A 3-level walk (3 indexes × ~50 entries) plus 2-3 concept reads is roughly 5-6k tokens and 4-6 tool turns per query, each turn re-sending context. reflect's hook delivers at most ~375 tokens (1,500 chars) per prompt with zero agent turns, at the cost of local compute and 12.8s p50 retrieval latency.
- Write side: OKF specifies no capture pipeline. reflect's drain spends Sonnet tokens per transcript (tracked in `~/.reflect/drain-cost.jsonl`).

## How to measure

Arms:
- R0: current reflect recall.
- O1: OKF index-navigation agent (Sonnet, tools: read `index.md` and concept files only) over an OKF export of the same KB.
- O2: reflect recall run on a KB re-imported from the OKF export (proves the projection is lossless for retrieval).

Datasets: the 20 golden queries, LOCOMO conv-26 (50 questions), and 30 real prompts sampled from `recall_log.jsonl` with hand-labelled relevant IDs.

Metrics: R@5, MRR, noise rate, LOCOMO J; tokens actually delivered to the model per query (measured at the hook boundary, or total API input+output tokens for O1 including every tool turn); tool calls per query; p50/p95 latency; dollars per query; write-side dollars per learning.

Prerequisite fixes so the numbers are honest: log post-truncation injected tokens; set `discovery_tokens` in the drain writer; skip recall on `<task-notification>` payloads.

## What to lift and shift

1. Backfill and normalize `type` (56% missing, two casings). Cheap, gives OKF conformance.
2. Derived trust tiers from `generated`/`verified` actors. Map to existing `authority`/`quarantine`; record `verified: human:<id>` when a user confirms a correction.
3. `stale_after` as an alias of `forget_after` on export/import.
4. Keyed per-claim source footnotes in drain-writer output (the drain writer currently writes no `provenance` block).
5. Generated `index.md` per shard/category as a zero-infra browse surface for harnesses without hooks.
6. Skip attested computation (BigQuery-specific); the nearest analogue is PreToolUse policy rules.

Upstream contribution opportunity: reflect's typed relations and supersession model answer OKF issues #16, #22, #11, #13.

## Supporting OKF as the standard: work required

- `reflect export --format okf <dir>`: map frontmatter (`type`, `title`, `description` ← `key_insight`, `tags`, `generated`, `verified`, `status` ← DB status with superseded → deprecated + successor link, `stale_after` ← `forget_after`, `sources[]` ← provenance). Keep reflect fields as extension keys (allowed by §11). Emit typed relations as an extension key plus a "Related" link section. Generate `index.md` per directory, root `okf_version: "0.2"`, `log.md` from `learning_history`.
- `reflect ingest` OKF provider: parse bundle, map trust tier to `confidence_num`, quarantine unverified external concepts, run rule-based entity extraction, reindex.
- `reflect okf lint`: a validator, since upstream ships none.
- Behavioural proof: export → import round-trip with identical golden-query results.
- Native on-disk OKF (making `documents/` itself a bundle) is possible but not recommended now: identity-by-path conflicts with reflect's ID schemes and shard layout, and the spec is still moving under one maintainer.

## Recommendations

1. Adopt OKF as an interchange projection (export + ingest + lint), not as the native store or retrieval model.
2. Run the three-arm benchmark before claiming any efficiency result.
3. Fix the three measurement defects first.
4. Backfill `type` now; it is independent and cheap.
