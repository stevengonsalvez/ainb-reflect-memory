Open Knowledge Format vs reflect: adopt, borrow, or ignore?

01

Recommendation

Support OKF as an export/import format. Keep reflect's own retrieval engine. Borrow 4 OKF ideas.
  • OKF is a file format, not a retrieval system. The spec says serving and search are out of scope. fact · SPEC §1
  • reflect notes are already markdown files with frontmatter. OKF conformance is mostly a backfill of the type field. fact · SPEC §11
  • 56% of sampled live notes have no type field (1,669 of 3,000). fact · measured today
  • OKF's most-requested open issues are typed relationships and supersession. reflect already has both. fact · issues #16 #22 #11
  • No benchmarks exist for OKF's approach of browsing index.md files. Any efficiency claim needs our own benchmark first. inference

How each system gets knowledge to the model

OKF: the agent browses to the right file. reflect: a hook searches and injects the result before the model reads the prompt.

04

Pros and cons: retrieval accuracy and tokens

Hypotheses until the benchmark in section 05 runs. Each box says what result would prove it wrong.

reflect (hook search and injection)

≤ ~375 tok delivered per prompt · 0 agent turns
  • + Keyword, vector and graph search handle 7.8k notes. Golden-query benchmark: R@5 1.0, MRR 0.94. fact
  • + Works without the agent choosing to look. fact
  • − p50 retrieval takes 12.8s and loads local models. fact
  • − Injects on every prompt, including system events: 26% of recalls in 30 days fired on <task-notification> text. fact
  • − A 20-query golden set and a 50-question LOCOMO pilot are small samples. inference

OKF (agent browses index files)

~5-6k tok per query · 4-6 tool turns (estimate)
  • + Zero infrastructure. Readable by any agent with cat, git diffs are readable. fact
  • + Only costs tokens when the agent decides it needs knowledge. inference
  • − No keyword or vector search. Recall depends on how good the one-line descriptions are. fact
  • − Sample bundles total 78 files. Nothing shows it working at thousands of notes. fact
  • − Every tool turn re-sends the whole context, so total tokens grow with the number of turns. inference

Proves it wrong: an index-browsing agent reaches R@5 ≥ 0.95 on the golden set using ≤ 1.5k tokens per query.

05

How we measure it

Three setups (arms), same questions, and tokens counted at the point they reach the model. Uses the existing tests/eval harness.

Arms

  • R0 reflect recall as it runs today.
  • O1 Sonnet agent with read-only tools, browsing an OKF export of the same KB.
  • O2 reflect recall over a KB exported to OKF and re-imported. Passes only if results match R0.

Datasets

  • 20 golden queries (tests/eval/fixtures/golden_queries.yaml).
  • LOCOMO conv-26, 50 questions (~$15 per arm).
  • 30 real prompts sampled from recall_log.jsonl, with the relevant note IDs labelled by hand.

Metrics

  • Accuracy R@5, MRR, noise rate, LOCOMO J.
  • Tokens Tokens delivered to the model per query. For O1: API input + output summed over all tool turns.
  • Cost $ per query; $ per learning written (write side).
  • Speed p50/p95 latency, tool calls per query.

Fix these first, or the numbers are wrong

  • recall_log.jsonl logs injected_tokens before the hook truncates to 1,500 chars. Logged p50 2,879 tok ≠ what the model receives. fact · recall.py:2622-2657
  • "D → R, tok saved" uses a default D (e.g. 2,000 for corrections) because the drain writer never sets discovery_tokens. fact · recall.py:400-407
  • Recall runs on <task-notification> payloads: 176 of 677 calls, ~599k logged tokens in 30 days. fact · recall_log.jsonl

07

Lift and shift

These are independent of the option chosen, except #5 which only matters for A or B.

  1. Backfill and normalise type. 56% of notes have none; the rest use two casings. This alone makes notes OKF-conformant. S · no dependencies
  2. Trust tiers. Record verified: human:<id> when a user confirms a correction. Derive the tier from who verified the note and map it to authority/quarantine. M · conflicts with Rule S9 (frontmatter never changes): keep it in the DB, write it only on export
  3. Per-claim source footnotes in single-shot writer output, and fill the provenance block the writer skips today. S
  4. stale_after as an alias of forget_after, as an absolute date. XS
  5. Generated index.md per shard so Codex/Copilot without hooks can browse by category. S · reuse the index stage of staged recall
  6. Skip attested computation. It is designed around BigQuery SQL and doesn't fit what we store. won't do

Other direction: reflect's typed relationships and supersession answer OKF issues #16, #22, #11 and #13. We could propose them upstream.

08

What supporting OKF takes (option A)

  1. reflect export --format okf <dir>. Field mapping: description ← key_insight, status ← DB status (superseded becomes deprecated, plus a link to the successor), stale_after ← forget_after, sources[] ← provenance, generated ← writer model + created. Keep reflect-only fields as extra keys (the spec allows them, §11).
  2. Graph out. Typed relations become an extension relationships: key plus a "Related" section of markdown links, so plain OKF readers still see the edges.
  3. Bundle files. An index.md in each directory, okf_version: "0.2" in the root index.md, and a log.md built from learning_history.
  4. OKF source for reflect ingest. Trust tier sets confidence_num (human 0.9 / machine 0.6 / none 0.3). Unverified external notes are quarantined. Rule-based entity extraction, then reindex. Same pattern as the existing 11 sources.
  5. reflect okf lint. Upstream ships no validator or JSON Schema (issue #8).
  6. Round-trip test in tests/eval/behavioral: export, import, then the golden queries must return the same results as before (this is arm O2).
09

Open questions

Rule S9 vs verified

OKF expects verified in frontmatter. Our Rule S9 says frontmatter never changes after writing. Proposed: keep it in the DB and write it into frontmatter only on export.

Export directory layout

By learning_type, by category, or by shard? This decides how good index.md browsing is.

Contribute upstream?

Typed relationships would close OKF's biggest gap. The maintainer has answered no issues yet, so the payoff is uncertain.

Is the spec stable enough?

It shipped a breaking timestamp change without a version bump (#24). Pin the export to v0.2 and version our mapping.
